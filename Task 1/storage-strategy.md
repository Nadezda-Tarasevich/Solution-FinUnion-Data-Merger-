### Целевая архитектура хранилищ данных FinUnion Group



#### 1\. Операционные данные (OLTP)

**Рекомендуемый тип:** Распределённая реляционная СУБД с поддержкой ACID (PostgreSQL с Patroni / Yandex Managed PostgreSQL / Oracle Exadata)

**Какие данные:** текущие записи: Клиенты (CRM), Договоры, Счета, Карты, Транзакции, Платежи, Обращения

**Обоснование**: Требуется ACID-транзакции, согласованность в реальном времени, высокая доступность (24/7). Объём данных — до 10 ТБ (активные данные), нагрузка — до 10 000 транзакций в секунду. NoSQL не подойдет так как финансовые данные требуют строгой согласованности и соблюдения стандартов (ЦБ РФ, PCI DSS). NoSQL не гарантирует ACID в распределённом режиме. Единая монолитная БД невозможна так как банк имеет несколько АБС (FU Core, RB Core) — полная миграция за 12 месяцев нереалистична. Распределённая архитектура (FU Core + RB Core с единым ESB) — прагматичный компромисс.

**Сроки**: 12 месяцев — целевая архитектура: единая АБС на базе FU Core с миграцией данных из RB Core.

#### 2\. Мастер-данные (MDM)

**Рекомендуемый тип:** Централизованная MDM-платформа (Informatica MDM / Semarchy / TIBCO EBX / самописное решение на базе PostgreSQL)

**Какие данные:** Золотые записи клиентов (Customer 360), единые справочники (Продукты, Типы счетов, Сегменты), клиентские иерархии

Обоснование: Единый источник правды для всей группы. Без MDM дубли клиентов, несогласованные справочники и ошибочная отчётность. DWH не походит так как это аналитический слой, не предназначенный для операционной синхронизации в реальном времени. MDM должен обновляться в near-real-time (CDC из OLTP). OLTP-системы (FU CRM, RB CRM) так же не подходит так как не является  единым источником правды. MDM — отдельный слой, который агрегирует и чистит данные из разных источников.

**Сроки**: 3 месяца — MVP (золотая запись клиента), 12 месяцев — полноценный MDM (все сущности, управление качеством, lineage).

#### 3\. Регламентированная отчётность (DWH)

**Рекомендуемый тип:** Колоночная СУБД (ClickHouse / Vertica / Greenplum / Snowflake)

**Какие данные:** Витрины данных для форм ЦБ, финансовой отчетности, управленческой отчётности.

**Обоснование:** Колоночные СУБД обеспечивают высокую скорость агрегаций (суммы, остатки, средние) на больших объёмах (10-100 млрд строк). Поддержка SQL, строгий контроль точности. Регламентированная отчётность требует строгой схемы (star schema), гарантированной точности и быстрого времени ответа (менее 5 сек для форм ЦБ). Data Lakehouse предпочтителен для исследовательской аналитики, а не для фиксированных отчётов. Так же отчётность не должна нагружать операционные системы (ограничение: “аналитика не должна создавать нагрузку на операционные системы”), поэтому OLTP так же не подходит для использования.

**Сроки:** 3 месяца — Fed DWH (сборка из FU DWH + RB DWH), 12 месяцев — целевой DWH на новой платформе.

#### 4\. Большие исторические и событийные данные (Data Lakehouse)

**Рекомендуемый тип:** Apache Iceberg / Delta Lake на объектном хранилище + Apache Spark / Trino для обработки

**Какие данные:** исторические транзакции (7+ лет), карточные операции, события (клики, логи, метрики фрода), стриминговые данные.

**Обоснование:** хранение сотен миллиардов записей с низкой стоимостью (объектное хранилище), ACID-транзакции на уровне таблиц (Iceberg), поддержка batch и streaming. Стоимость хранения в DWH (колоночные СУБД) в 5-10 раз выше, чем в Data Lakehouse. Для исторических данных, к которым обращаются редко, это неэффективно.

**Сроки:** 12 месяцев — полный Data Lakehouse (все исторические данные из FU и RB консолидированы).

#### 5\. Неструктурированные данные (Объектное хранилище)

**Рекомендуемый тип:** S3-совместимое объектное хранилище (Min.io / AWS S3 / Yandex Object Storage / Ceph)

**Какие данные:** Сканы документов (паспорта, договоры), записи звонков, скриншоты обращений, логи, архивные выгрузки.

**Обоснование:** неструктурированные данные большого объёма (10+ ТБ), неэффективно хранить в БД. Объектное хранилище — стандарт для таких данных.

**Сроки:** 6 месяцев — активное хранилище (документы до 3 лет), 12 месяцев — архив (данные старше 3 лет с автоматическим переходом в Glacier).



#### 6\. Связи клиентов и контрагентов (Графовая БД)

**Рекомендуемый тип:** Neo4j (графовая система управления БД) (или Amazon Neptune, если облако)

**Какие данные**: иерархии юрлиц (холдинги, дочерние компании), родственные связи физлиц, цепочки платежей (для AML), связи “сотрудник — клиент”.

**Обоснование**: Графовая БД эффективна для обхода связей глубиной 3+ уровней (например, “кто владеет компанией, которая переводит деньги компании, которой владеет родственник”). В реляционной БД такие запросы требуют 10+ JOIN и выполняются минутами.

**Сроки**: 12 месяцев (после построения MDM — клиентские данные должны быть чистыми).

#### 7\. Быстрый поиск (Поисковый движок)

**Рекомендуемый тип**: Elasticsearch (или OpenSearch)

**Какие данные:** индексы для полнотекстового поиска по: клиентам (ФИО, ИНН, телефон, паспорт — маскированный), обращениям (тема, текст), транзакциям (RRN, сумма, дата).

**Обоснование**:	Поиск по 50+ млн записей за 1-2 секунды с fuzzy-поиском (опечатки в ФИО), агрегациями (количество обращений по теме). Elasticsearch — стандарт для таких задач.

**Сроки**:6 месяцев (совместно с объектным хранилищем — индексация обращений и документов).
