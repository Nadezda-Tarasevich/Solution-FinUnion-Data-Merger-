### Основные потоки данных FinUnion Group (промежуточное состояние, 3 месяца)



|Источник|Приёмник|Передаваемые сущности|Тип действия с данными|Режим обмена|Обоснование|
|:-:|:-:|:-:|:-:|:-:|:-:|
|Клиент|FU CRM, RB CRM|Клиент (создание/обновление), Обращение|Create/Update|Синхронный (онлайн)|Клиент взаимодействует с банком через CRM (веб/мобильное приложение/офис). Данные должны быть актуальны сразу после ввода.|
|FU CRM, RB CRM|FU Core, RB Core|Клиент, Договор (новые), Счёт (на открытие)|Create/Update|Синхронный (онлайн)|После создания клиента в CRM, договор и счёт должны создаваться в АБС в реальном времени для проведения операций.|
|FU Core, RB Core|FU Cards, RB Cards|Счёт (для выпуска карты), Договор (для кредитной карты)|Create/Update|Синхронный (онлайн)|Для выпуска карты нужен актуальный счёт в АБС. Карта привязывается к счёту в момент выпуска.|
|FU Core, RB Core|FU DWH, RB DWH|Счёт, Договор, Транзакция (остатки, движения)|Read (batch)|Batch (ежедневно, каждые 15 мин)|DWH строится на выгрузках из АБС для отчётности. Batch-режим не нагружает операционную АБС (ограничение: “аналитика не должна создавать нагрузку на операционные системы”).|
|FU Cards, RB Cards|FU DWH, RB DWH|Карта, Транзакция (карточные операции)|Read (batch)|Batch (ежедневно)|Карточные операции выгружаются из процессинга в DWH для анализа расходов, комиссий и фрод-мониторинга.|
|FU Core, FU Cards, FU CRM|FU Data Lake|Транзакция (сырые), События (логи), Документы (скан паспорта, заявления)|Create|Streaming (Kafka) + Batch (ежедневно)|Data Lake хранит сырые/неструктурированные данные для построения ML-моделей (фрод, скоринг) и долгосрочного хранения (>3 лет). Streaming — для событий (карты, логи), Batch — для документов.|
|FU Data Lake|Fed DWH|Исторические транзакции (старше 3 лет), сырые события|Read/Enrich|Batch (еженедельно)|Исторические данные из Data Lake обогащают отчётность Fed DWH (например, для форм ЦБ за 5 лет). Без этого потока Data Lake — “мёртвое хранилище”.|
|FU CRM, RB CRM|ESB|Клиент (события создания/изменения)|Create/Update|Асинхронный (Kafka)|События о клиентах отправляются в ESB для матчинга в MDM. Асинхронный режим не блокирует CRM (клиент не ждёт ответа от MDM).|
|FU Core, RB Core|ESB|Договор, Счёт (события создания/изменения)|Create/Update|Асинхронный (Kafka)|События об изменении договоров/счетов отправляются в ESB для синхронизации с Fed DWH и другими системами.|
|ESB|MDM|Клиент (данные для матчинга и дедубликации)|Create/Update|Асинхронный (Kafka)|ESB передаёт клиентские данные из CRM в MDM для построения золотой записи. Асинхронный режим позволяет MDM обрабатывать данные без задержек для CRM.|
|MDM|ESB|Клиент (золотая запись, golden\_id, статус дубля), Продукт (справочник), Сегмент (справочник)|Enrich/Read|Асинхронный (Kafka)|MDM возвращает золотой ID и маппинг дублей в ESB для распространения в CRM и другие системы.|
|MDM|FU CRM, RB CRM|Клиент (золотой ID, маппинг дублей)|Update|Асинхронный (Kafka)|MDM обновляет CRM: проставляет golden\_id, помечает дубли. Это нужно, чтобы сотрудники видели единого клиента.|
|ESB|Fed DWH|Клиент (golden\_id), Договор, Счёт (обогащённые данными MDM)|Enrich/Create|Асинхронный (Kafka)|ESB передаёт в Fed DWH обогащённые данные (с golden\_id) для построения витрин отчётности.|
|FU DWH, RB DWH|Fed DWH|Все сущности: Клиент, Счёт, Договор, Карта, Транзакция (агрегированные)|Read/Validate/Aggregate|Batch (ежедневно)|Fed DWH консолидирует данные из двух DWH для единой отчётности. Выполняется валидация (проверка дублей, форматов) и агрегация (группировка по клиентам, продуктам).|
|Fed DWH|BI (единая отчётность)|Витрины данных (агрегированные по клиентам, счетам, продуктам, операциям)|Read/Aggregate|Синхронный (SQL-запрос)|BI строит дашборды и отчёты на основе витрин Fed DWH. Синхронный режим — аналитик запрашивает отчёт и получает его сразу.|
|Fed DWH|Регулятор (ЦБ РФ)|Формы ЦБ, МСФО-отчётность|Read/Validate|Batch (ежемесячно, ежеквартально)|Регуляторная отчётность формируется на основе Fed DWH. Валидация перед отправкой (проверка контрольных сумм, форматов ЦБ). Batch — по расписанию ЦБ.|
