### README: Целевая архитектура данных FinUnion Group


Обзор проекта
---


Данный документ описывает целевую архитектуру данных, разработанную для объединённой компании FinUnion Group после слияния с RetailBank. Архитектура охватывает полный жизненный цикл данных — от операционных систем до аналитических хранилищ и Data Products, — и рассчитана на поэтапное внедрение в течение 12 месяцев.

1. ###### target-data-architecture.md/target-data-architecture.pdf - wелевая архитектура данных (To-Be, 12 месяцев)


Архитектура построена по принципу разделения операционных и аналитических нагрузок и включает следующие ключевые слои.

**Операционный слой (OLTP)** состоит из единой АБС на базе FU Core, единой CRM на базе FU CRM, единого карточного процессинга FU Cards и единой кредитной системы FU Loans. Все системы RetailBank отключаются после миграции данных.

**Канальный слой** включает веб-приложение, мобильное приложение, офисы и контакт-центр. Все запросы клиентов и сотрудников проходят через единый API Gateway, который обеспечивает аутентификацию, маршрутизацию и логирование.

**Интеграционный слой** построен на трёх компонентах: ESB для синхронного обмена между операционными системами, Kafka для асинхронных событийных потоков и Debezium для захвата изменений данных (CDC) из операционных БД в реальном времени.

**Слой мастер-данных** реализован через MDM (Customer Hub), который хранит золотые записи клиентов, единые справочники продуктов и сегментов. MDM получает данные через Kafka, выполняет матчинг по ИНН, паспорту или СНИЛС и возвращает golden\_id обратно в операционные системы.

**Аналитический слой** состоит из трёх компонентов: Data Lakehouse на базе Apache Iceberg и Spark для хранения сырых исторических и событийных данных, DWH на ClickHouse для регламентированной отчётности и BI для дашбордов и витрин.

**Слой оркестрации и управления** включает Apache Airflow для управления batch-пайплайнами и DataHub для каталога данных, lineage и управления владельцами.

Все потребители — аналитики, регулятор, риск-менеджмент, антифрод и Data Science — получают данные только из аналитического слоя, минуя операционные системы.





2. ###### architecture-options.md- Сравнение архитектурных подходов


Были рассмотрены три подхода к организации аналитической архитектуры: классический DWH на PostgreSQL, Data Lakehouse и Data Mesh.

**DWH на PostgreSQL** обеспечивает простоту внедрения, строгую схему и полную ACID-транзакцию, но ограничен по объёму данных (до 10–20 ТБ), не поддерживает потоковую обработку и имеет высокую стоимость хранения больших объёмов.

**Data Lakehouse** на базе Iceberg и Spark обеспечивает дешёвое хранение на S3, поддержку streaming и schema evolution, но требует высокой квалификации команды, имеет более сложное обеспечение ACID и уступает в скорости на регламентированных витринах малого объёма.

**Data Mesh** предлагает децентрализацию данных по доменам с чёткими Data Products и SLA, но требует зрелой культуры Data Governance, организационных изменений и не менее 10–15 доменов для оправдания сложности. На этапе 12 месяцев после слияния такой подход преждевременен.

В качестве **целевого решения** выбрана гибридная архитектура: DWH на ClickHouse для регламентированной отчётности и Data Lakehouse на Iceberg и Spark для исторических, событийных и ML-данных. Такое сочетание обеспечивает скорость и точность для форм ЦБ за счёт DWH, и дешёвое масштабируемое хранение для сырых данных — за счёт Lakehouse.

4. ###### data-pipelines.md/data-pipelines.pdf- Пайплайны данных


Разработаны ключевые пайплайна, охватывающих как промежуточное, так и целевое состояние.

**Первый пайплайн** работает в промежуточном состоянии (3 месяца) и выполняет ежедневную batch-загрузку данных из FU DWH и RB DWH в Fed DWH на PostgreSQL. Использует Airflow, SQL и Foreign Data Wrappers для прямого чтения из источников. Обеспечивает базовую отчётность и дедубликацию клиентов по ИНН.

**Второй пайплайн** — streaming-пайплайн CDC через Kafka в Data Lakehouse. Debezium захватывает изменения из WAL PostgreSQL, публикует их в Kafka, а Spark Structured Streaming записывает в Iceberg-таблицы. Обеспечивает задержку менее 5 минут и exactly-once семантику.

**Третий пайплайн** — ежедневный ELT из Lakehouse в DWH для формирования витрин регламентированной отчётности. Spark читает данные из Iceberg за последние 24 часа, выполняет агрегацию и записывает результат в ClickHouse. Включает валидацию контрольных сумм.



###### 5\. analytical-model.md/analytical-model.pdf- Аналитическая модель


Для области анализа транзакций выбрана схема «звезда» как наиболее подходящая для OLAP-нагрузки в ClickHouse.

Центральная таблица фактов fact\_transaction содержит 15 миллиардов записей с ключами на шесть измерений: клиент, счёт, продукт, отделение, дата и канал. Измерения денормализованы: сегмент и регион клиента хранятся строками в dim\_client, категория продукта — строкой в dim\_product, иерархия даты (год, квартал, месяц, день) — в dim\_date.

Схема «звезда» выбрана, поскольку обеспечивает минимальное количество JOIN (шесть вместо десяти и более в схеме «снежинка»), что критически важно для производительности ClickHouse. Денормализация измерений добавляет около 5–10 процентов избыточности, но не влияет на скорость запросов благодаря колоночному хранению. Все BI-инструменты поддерживают эту схему, а аналитики пишут простые и понятные SQL-запросы.



###### 6\. data-products.md - Data Mesh и Data Products


В целевой архитектуре реализованы элементы Data Mesh через выделение доменных Data Products, каждый из которых привязан к области BIAN, имеет назначенного владельца и чёткий круг потребителей.

Data Product Customer 360 относится к домену Party Reference Data Directory, управляется Data Office и включает золотую запись клиента с golden\_id, контактами, сегментом и скоринговым баллом. Потребители — CRM, контакт-центр, маркетинг и риск-менеджмент.

Data Product Payment Flow относится к домену Payment Execution, управляется департаментом РКО и содержит все транзакции и платежи с признаками фрода. Потребители — финансовый департамент, антифрод и регулятор.

Data Product Card Portfolio относится к домену Card Management, управляется карточным департаментом и включает карты, лимиты и карточные транзакции. Потребители — антифрод, контакт-центр и маркетинг.

Data Product Customer Interaction относится к домену Customer Relationship Management, управляется контакт-центром и включает обращения, заявки и записи звонков. Потребители — контакт-центр, маркетинг и риск-менеджмент.

Data Product Product Catalog относится к доменам Product Catalog и Product Design, управляется продуктовым департаментом и содержит единый справочник продуктов и тарифов. Потребители — CRM, BI и маркетинг.

Каждый Data Product имеет назначенного владельца из числа бизнес-подразделений, опубликован через DataHub с полным lineage, и доступен потребителям через единый аналитический слой (ClickHouse для витрин, API для операционных систем).
