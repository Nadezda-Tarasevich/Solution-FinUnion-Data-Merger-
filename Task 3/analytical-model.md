### Аналитическая модель: Схема «Звезда» для области анализа транзакций



1. ###### Выбор схемы: «Звезда» (Star Schema)

|Аспект|Схема «Звезда»|Схема «Снежинка»|
|:-:|:-:|:-:|
|Структура|Одна центральная таблица фактов, связанная с несколькими денормализованными таблицами измерений|Таблицы измерений нормализованы (разбиты на подтаблицы)|
|Количество JOIN|1 JOIN на каждое измерение (минимум)|2+ JOIN на каждое измерение (из-за нормализации)|
|Простота запросов|Высокая — SELECT с 3-5 JOIN|Низкая — SELECT с 5-10 JOIN|
|Производительность OLAP|Высокая — меньше JOIN, колоночное хранение|Средняя — больше JOIN, выше нагрузка|
|Дублирование данных|Есть (денормализация измерений)|Минимальное (нормализация)|
|Гибкость изменений|Средняя (изменение измерения требует обновления всех строк)|Высокая (изменение в одном месте)|

Обоснование:

Производительность OLAP: В схеме «звезда» для получения данных о транзакции достаточно 3-5 JOIN (таблица фактов + 3-5 измерений). В схеме «снежинка» — 6-12 JOIN (из-за нормализации измерений). Для ClickHouse (колоночная СУБД) JOIN — дорогая операция. Меньше JOIN = быстрее запросы.

Простота для аналитиков: Бизнес-аналитики пишут SQL-запросы, в схеме «снежинка» запрос был бы в 2 раза длиннее (дополнительные JOIN для типа клиента, категории продукта).

Колоночное хранение: ClickHouse хранит данные по колонкам. Денормализованные измерения (например, client\_name в dim\_client) занимают немного места и не влияют на производительность. Нормализация не даёт выигрыша.

Частота изменений измерений: Измерения (клиенты, продукты, отделения) меняются редко (1-2% записей в месяц). Дублирование незначительно (10-20% избыточности).

###### 3\. Обоснование выбора схемы «Звезда» для OLAP-нагрузки

|Требование OLAP|Как схема «Звезда» удовлетворяет|Пример|
|:-:|:-:|:-:|
|Быстрые агрегации (SUM, COUNT, AVG)|Колоночное хранение ClickHouse + один проход по фактам. Меньше JOIN — быстрее агрегация.|SELECT SUM(amount) FROM fact\_transaction WHERE date\_id = '...' — 0.5 сек на 15 млрд строк|
|Фильтрация по измерениям|Измерения денормализованы — фильтр применяется к одному полю (не JOIN).|WHERE region = 'Москва' AND client\_type = 'ЮрЛицо' — все поля в dim\_client|
|Drill-down по иерархиям|Иерархия даты (год → квартал → месяц → день) — в одном измерении dim\_date.|GROUP BY year, month — без дополнительных JOIN|
|Sliding window (окна по времени)|Партиционирование по дате + сортировка по date\_id.|WHERE date\_id >= '2024-01-01' AND date\_id < '2025-01-01' — partition pruning|
|Множественные измерения (5-6)|6 измерений → 6 JOIN. Для ClickHouse — оптимально (не более 8 Join).|Запрос с JOIN всех 6 измерений выполняется за 3-5 секунд|
|Исторические данные (15 млрд строк)|ClickHouse + партиционирование + колоночное хранение = 100 MB/сек сканирование|Полное сканирование за месяц (500 млн строк) — 5 секунд|
|Поддержка BI-инструментов|Все BI-инструменты (Superset, Tableau, Power BI) поддерживают схему «Звезда»|Drag-and-drop измерений в дашборде|
