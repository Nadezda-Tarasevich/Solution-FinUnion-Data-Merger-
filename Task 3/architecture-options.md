###### Почему не выбран каждый из чистых подходов

1. ###### Почему не чистый DWH на PostgreSQL

Объём данных: Исторические транзакции FinUnion + RetailBank = 100+ млрд строк. PostgreSQL имеет ограничения по объёму (10-20 ТБ активных данных оптимально).
Неструктурированные данные: Документы, аудиозаписи звонков, сканы договоров — не могут храниться в реляционной БД.
ML-модели: Для фрод-мониторинга и скоринга нужны сырые данные (без агрегации). DWH хранит только агрегированные витрины.
Streaming: DWH не предназначен для потоковой обработки (транзакции из Kafka в реальном времени).

2. ###### Почему не чистый Data Lakehouse

Регламентированная отчётность: Формы ЦБ и МСФО требуют строгой схемы, ACID-транзакций и гарантированной точности (0 ошибок). Data Lakehouse (Iceberg) обеспечивает ACID на уровне файлов, но не на уровне запросов.
Производительность: На малых витринах (до 1 млрд строк) ClickHouse работает в 10-100 раз быстрее, чем Spark/Trino.
Команда: У FinUnion есть экспертиза PostgreSQL и SQL, но нет сильной команды Spark. DWH — быстрее внедрить.

3. ###### Почему не чистый Data Mesh

Организационная зрелость: На 12 месяцев после слияния нет Data Owners во всех доменах. Внедрение Data Mesh требует 2-3 лет.
Количество доменов: Всего 5-6 доменов (розница, МСБ, карты, кредиты, финансы, риски). Для Data Mesh нужно 10+ доменов, чтобы оправдать сложность.
Инфраструктура: Data Mesh требует единой платформы (DataHub, Airflow, Kafka) — это уже есть в гибридной архитектуре. Чистый Data Mesh добавил бы только организационную сложность.
