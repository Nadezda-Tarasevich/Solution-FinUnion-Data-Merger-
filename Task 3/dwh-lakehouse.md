### Сравнение DWH на PostgreSQL и Data Lakehouse для кейса FinUnion + RetailBank

1. ###### Сводная таблица сравнения



|Критерий|DWH на PostgreSQL|Data Lakehouse (Iceberg + Spark + Trino)|
|:-:|:-:|:-:|
|Объём данных|Оптимально до 10-20 ТБ (активные данные). Свыше — деградация производительности.|100+ ТБ (исторические данные). Горизонтальное масштабирование (S3 + Spark).|
|Стоимость хранения|\~$20-50/TB/мес (EBS/SSD). Высокая стоимость для больших объёмов.|\~$3-5/TB/мес (S3 Standard). Низкая стоимость.|
|Стоимость вычислений|Включена в стоимость БД. Фиксированная мощность.|Отдельно: $0.10-0.50/GB обработанных данных (Spark/Trino). Pay-as-you-go.|
|Скорость запросов|Быстро (1-10 сек) на регламентированных витринах (звёздная схема). Медленно на сырых данных (100+ сек).|Медленно (10-60 сек) на регламентированных витринах (накладные расходы Spark). Быстро (5-30 сек) на сырых данных (Trino, партиционирование).|
|Поддержка ACID|Полная ACID (транзакции, изоляция).|ACID на уровне файлов (Iceberg), не на уровне запросов. Компенсация через snapshot isolation.|
|Schema evolution|Сложно (ALTER TABLE — блокировки, даунтайм).|Просто (Iceberg: ADD/DROP/RENAME COLUMN без перезаписи).|
|Поддержка streaming|Нет нативной поддержки (только batch через COPY).|Нативная поддержка (Spark Structured Streaming + Iceberg).|
|Поддержка ML/Data Science|Ограничена (только агрегированные данные).|Полная (сырые данные, Python/Spark MLlib, Jupyter).|
|Навыки команды|Низкий порог (SQL, PostgreSQL администрирование).|Высокий порог (Spark, Kafka, Iceberg, Trino, Airflow).|
|Зрелость технологии|30+ лет. Стабильность, предсказуемость.|5-7 лет (Iceberg — 2018, Trino — 2019). Быстрое развитие, но меньше проверенных кейсов в банках.|
|Интеграция с BI|Прямая (все BI-инструменты поддерживают PostgreSQL).|Через слой SQL (Trino/Presto) или через DWH (ClickHouse).|

2. ###### Выбранный подход



Промежуточное состояние (3 месяца) - DWH на PostgreSQL (Fed DWH)
Обоснование: PostgreSQL — знакомая технология для команды FinUnion. Не требует найма Spark-инженеров. Fed DWH можно собрать за 3 месяца: Airflow + SQL + FDW. Первоочередная потребность — сдавать отчётность в ЦБ. PostgreSQL обеспечивает строгую схему, ACID и быстрые агрегации. Объем данных на 3 месяца -
только активные данные (FU DWH + RB DWH за последний год), занимают ориентировочно 2-3 TB — комфортный объём для PostgreSQL.Меньше точек отказа: не нужны Kafka, Spark, Iceberg.



Целевая Гибридная архитектура (DWH + Data Lakehouse)

|Компонент|Роль|Технология|
|:-:|:-:|:-:|
|DWH (ClickHouse)|Регламентированная отчётность (формы ЦБ, МСФО, управленческая). Быстрые агрегации на витринах.|ClickHouse (колоночная СУБД, быстрее PostgreSQL на больших объёмах)|
|Data Lakehouse (Iceberg + Spark + Trino)|Хранение сырых исторических данных, событий (Kafka), ML-данных. Основное хранилище для аналитики.|Apache Iceberg (формат таблиц), Apache Spark (ELT), Trino (SQL-запросы)|
|Связка|Lakehouse → DWH (ELT, ежедневно). DWH — надстройка для регламентированной отчётности.|Airflow (оркестрация)|



Почему не чистый Lakehouse:

Регламентированная отчётность требует строгой схемы и гарантированной точности (0 ошибок). Lakehouse обеспечивает ACID на уровне файлов, но не на уровне сложных запросов (JOIN нескольких таблиц).
ClickHouse в 10-100 раз быстрее Spark/Trino на витринах малого объёма (до 1 млрд строк) — а это и есть формы ЦБ.
Команда FinUnion уже знает SQL и PostgreSQL. ClickHouse — колоночная СУБД с SQL-синтаксисом, близким к PostgreSQL.



Почему не чистый DWH:
Исторические данные (15 млрд строк, 3.7 TB) в PostgreSQL будут слишком дорогими и медленными.
DWH не поддерживает streaming (CDC → Kafka) и неструктурированные данные (документы, аудио).
Для ML-моделей нужны сырые данные, а не агрегированные витрины.





3. ###### Роль Apache Iceberg и Trino



Apache Iceberg - это основной формат хранения данных в Data Lakehouse. Все исторические и событийные данные хранятся в Iceberg-таблицах на S3.
Ключевые возможности:

1. ACID-транзакции на уровне таблиц (commit, rollback).
2. Schema evolution: добавление/удаление полей без перезаписи.
3. Time travel: чтение данных на определённый момент времени (для аудита).
4. Hidden partitioning: автоматическое партиционирование по дате.
5. Compaction: оптимизация мелких файлов в крупные (128 MB



trino - распределённый SQL-движок для запросов к данным в разных источниках (Iceberg, PostgreSQL, Kafka, Elasticsearch) без перемещения данных.
Ключевые возможности:

1. Ad-hoc аналитика: аналитики пишут SQL-запросы к сырым данным в Iceberg.
2. BI-интеграция: Superset/Tableau подключаются к Trino как к PostgreSQL.
3. Объединение данных: JOIN между Iceberg и PostgreSQL (MDM, DWH).



###### 4\. Распределение данных: DWH vs Lakehouse

|Тип данных|Хранилище|Обоснование|
|:-:|:-:|:-:|
|Регламентированная отчётность (формы ЦБ, МСФО)|DWH (ClickHouse)|Требует строгой схемы, ACID, быстрых агрегаций. ClickHouse в 100 раз быстрее Spark на витринах малого объёма.|
|Управленческая отчётность (доходы, клиенты, продукты)|DWH (ClickHouse)|Ежедневные отчёты, фиксированная схема. Должны быть доступны за 1-2 секунды.|
|Агрегированные витрины для BI|DWH (ClickHouse)|Быстрые дашборды (менее 10 секунд). ClickHouse оптимизирован для OLAP-запросов.|
|Исторические транзакции (FU + RB, 3-7 лет, 15 млрд строк)|Data Lakehouse (Iceberg на S3)|Слишком большой объём для DWH (3.7 TB). S3 — дешёвое хранение. Iceberg — ACID и schema evolution.|
|Событийные данные (Kafka, CDC)|Data Lakehouse (Iceberg через Spark Streaming)|DWH не поддерживает streaming. Iceberg — нативная поддержка через Spark.|
|Сырые данные для ML (транзакции, события, логи)|Data Lakehouse (Iceberg на S3)|Data Science нужны сырые данные. DWH хранит только агрегированные витрины.|
|Архивные данные (старше 7 лет)|Объектное хранилище (S3 Glacier)|Экстремально дешёвое хранение ($1/TB/мес). Данные не требуют быстрого доступа.|
|Документы, аудио (сканы договоров, записи звонков)|Объектное хранилище (S3 Standard + Glacier)|Неструктурированные данные. Неэффективно хранить в DWH или Lakehouse.|
|MDM / Справочники (клиенты, продукты, сегменты)|MDM (PostgreSQL)|Операционные данные. Должны обновляться в реальном времени и быть ACID.|
|Агрегированные данные для риск-менеджмента (просрочки, PD, LGD)|DWH (ClickHouse)|Ежедневный расчёт, строгая схема. ClickHouse быстрее Spark.|
|ML-фичи (для скоринга, фрода)|Data Lakehouse (Iceberg + Spark)|Feature engineering требует сырых данных и Spark. Готовые фичи — в DWH для операционного использования.|



5. ###### Ограничения выбранного подхода



|Ограничение|Описание|Как смягчается|
|:-:|:-:|:-:|
|1. Сложность эксплуатации|Два хранилища (DWH + Lakehouse) вместо одного. Нужны навыки: ClickHouse, Spark, Iceberg, Trino, Kafka, Airflow.|Обучение команды (3-6 месяцев). Наём 2-3 Spark-инженеров. Использование managed-сервисов (Databricks, Confluent Cloud) для снижения сложности.|
|2. Задержка данных в DWH|DWH обновляется раз в сутки (batch). Данные за сегодня недоступны в витринах до следующего утра.|1. Streaming-витрины в ClickHouse (через Kafka → ClickHouse) — для критичных метрик (остатки, просрочки). 2. Lakehouse → Trino для запросов к текущим данным.|
|3. Риск рассинхронизации|Если ELT Lakehouse → DWH даёт сбой, витрины в DWH устаревают на 1 день.|Airflow: мониторинг, алерты, автоматический retry (3 попытки). DataHub: lineage для быстрого обнаружения источника ошибки.|
|4. ACID только на уровне таблиц|Iceberg не поддерживает ACID на уровне запросов (JOIN нескольких таблиц). Возможны “фантомные” чтения при одновременной записи и чтении.|1. Использовать snapshot isolation (читать зафиксированные данные на момент времени). 2. Для регламентированной отчётности — только DWH с полным ACID.|
|5. Производительность Trino|На запросах с объединением нескольких таблиц (3+ JOIN) может быть медленнее, чем ClickHouse.|Оптимизация: партиционирование, bucketing, материализованные представления. Для сложных запросов — Spark (быстрее, но дольше запуск).|
|6. Стоимость|DWH (ClickHouse) + Lakehouse (S3 + Spark/Trino) + Kafka — дороже, чем один чистый DWH.|Lakehouse снижает стоимость хранения (S3 vs SSD). Общая стоимость TCO за 5 лет — ниже, чем чистый DWH на PostgreSQL из-за дешёвого хранения исторических данных.|
|7. Миграция данных между хранилищами|При ELT Lakehouse → DWH возможна потеря данных при сбое.|Idempotent ELT (повторный запуск не создаёт дубли). DataHub lineage для трассировки.|
