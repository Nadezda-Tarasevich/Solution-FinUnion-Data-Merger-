### Сводная таблица целевой архитектуры FinUnion Group To-Be (12 месяцев)



1. #### Операционный слой (OLTP)

|Компонент|Назначение|Системы-замены (As-Is → To-Be)|Технология|Обоснование выбора|Ключевые сущности|Принцип работы|
|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
|Единая АБС (FU Core)|Центральная банковская система для управления счетами, договорами, платежами и остатками.|FU Core + RB Core → FU Core (RB Core отключена)|PostgreSQL (кластер Patroni) или Oracle Exadata|FU Core выбрана как более современная и гибкая АБС. RB Core — legacy-система, её замена стратегически оправдана. PostgreSQL обеспечивает ACID, высокую доступность и низкую стоимость владения по сравнению с Oracle.|Счёт, Договор, Платёж, Транзакция|Операции в реальном времени (OLTP). ACID-транзакции. Высокая доступность (99.99%).|
|Единая CRM (FU CRM)|Управление взаимодействиями с клиентами: обращения, заявки, история обслуживания.|FU CRM + RB CRM → FU CRM (RB CRM отключена)|Salesforce / MS Dynamics / самописное на PostgreSQL|FU CRM выбрана как база для единой CRM. RB CRM отключается после миграции всех обращений. Единая CRM обеспечивает единый интерфейс для контакт-центра, офисов и цифровых каналов.|Клиент, Обращение, Заявка|Операции в реальном времени (OLTP). Интеграция с API Gateway.|
|Единый карточный процессинг (FU Cards)|Управление жизненным циклом платёжных карт: выпуск, блокировка, перевыпуск, авторизация.|FU Cards + RB Cards → FU Cards (RB Cards отключён)|SmartVista / Way4 / самописное|FU Cards — более современный процессинг, соответствующий PCI DSS. Карты RB Cards не мигрируются физически, а перевыпускаются в FU Cards по истечении срока.|Карта, Транзакция (карточная), Лимит|Операции в реальном времени (OLTP). Изолирован в отдельном сегменте сети (PCI DSS).|
|Единая кредитная система (FU Loans)|Управление кредитными продуктами: выдача, обслуживание, мониторинг просрочек.|FU Loans + RB Loans → FU Loans (RB Loans отключена)|Самописное на PostgreSQL + Decision Engine|FU Loans — единая система для всех кредитных продуктов (розница + МСБ). RB Loans отключается после миграции договоров.|Кредит, Лимит, График платежей, Просрочка|Операции в реальном времени (OLTP). Интеграция с скоринговым движком.|

2. #### Интеграционный слой

|Компонент|Назначение|Технология|Обоснование выбора|Принцип работы|
|:-:|:-:|:-:|:-:|:-:|
|API Gateway|Единая точка входа для всех внешних запросов (клиенты, сотрудники, партнёры). Обеспечивает аутентификацию, авторизацию, rate limiting, маршрутизацию.|Kong / NGINX + Lua / AWS API Gateway|API Gateway разгружает операционные системы от задач аутентификации и защиты. Обеспечивает единый интерфейс для всех каналов (веб, мобильное приложение, офисы, контакт-центр).|Синхронные запросы (REST/SOAP). Маршрутизация в CRM, Core, Cards. Логирование всех запросов.|
|ESB (Enterprise Service Bus)|Внутренняя шина для синхронного обмена между операционными системами. Обеспечивает трансформацию форматов, маршрутизацию, надежность (retry, dead letter).|Apache Camel / MuleSoft / IBM Integration Bus|ESB необходим для слабой связанности между CRM, Core, Cards, Loans. Без ESB системы общаются напрямую (point-to-point), что усложняет поддержку и масштабирование.|Синхронные вызовы (SOAP/REST) между OLTP-системами. Трансформация XML↔JSON.|
|Kafka|Центральная событийная шина для асинхронных потоков данных. Используется для CDC, событий, интеграции с MDM и аналитическим слоем.|Apache Kafka + Schema Registry|Kafka обеспечивает exactly-once семантику, высокую пропускную способность (миллионы событий в секунду) и долговременное хранение событий. Необходима для построения событийно-ориентированной архитектуры.|Асинхронные потоки (Avro). Подписка: CDC → Kafka → MDM, Kafka → Lakehouse.|
|CDC Connectors (Debezium)|Захват изменений данных из операционных БД (PostgreSQL/Oracle) в реальном времени.|Debezium + Kafka Connect|CDC обеспечивает бесшовную синхронизацию изменений без нагрузки на операционные БД (нет двойной записи). Exactly-once гарантирует, что ни одно изменение не потеряно.|Streaming: БД → Kafka (изменения строк). Настраивается для каждой таблицы (клиенты, счета, договоры).|

3. #### Слой мастер-данных (MDM)

|Компонент|Назначение|Технология|Обоснование выбора|Ключевые сущности|Принцип работы|
|:-:|:-:|:-:|:-:|:-:|:-:|
|MDM (Customer Hub)|Централизованное управление мастер-данными: золотые записи клиентов, единые справочники продуктов, сегментов и типов.|Informatica MDM / Semarchy / самописное на PostgreSQL|MDM — единственный источник правды для клиентских данных. Без MDM клиенты дублируются, справочники расходятся, отчётность ошибочна. MDM получает данные из Kafka (CDC), выполняет матчинг по ИНН/паспорту/СНИЛС и возвращает golden\_id.|Клиент (золотая запись), Продукт, Сегмент, Справочники|Асинхронный (Kafka). Матчинг: правила (ИНН, паспорт, СНИЛС, телефон). Возврат golden\_id в ESB → CRM.|

4. #### Аналитический слой (OLAP)

|Назначение|Технология|Обоснование выбора|Ключевые сущности|Принцип работы||
|:-:|:-:|:-:|:-:|:-:|-|
|DWH (Хранилище данных)|Регламентированная отчётность: формы ЦБ (0409101, 0409155), МСФО, управленческая отчётность.|ClickHouse / Vertica / Greenplum|Колоночные СУБД обеспечивают скорость агрегаций на больших объёмах (10-100 млрд строк) и строгий контроль точности. DWH не должен нагружать операционные системы.|Витрины: Клиент, Счёт, Транзакция, Кредит|Batch-загрузка из Lakehouse (ELT). SQL-запросы для BI. Витрины для форм ЦБ.|
|Data Lakehouse|Хранилище для больших исторических и событийных данных: сырые транзакции, события из Kafka, логи, ML-данные.|Apache Iceberg / Delta Lake на S3 + Apache Spark / Trino|Data Lakehouse обеспечивает низкую стоимость хранения (S3), ACID-транзакции (Iceberg), schema evolution и поддержку batch и streaming. Используется для ML-моделей (фрод, скоринг) и исследовательской аналитики.|Транзакция (сырые), События, Логи, Документы|Streaming (Kafka → Lakehouse) + Batch (Core → Lakehouse). ELT → DWH.|
|BI (Бизнес-аналитика)|Дашборды, витрины, аналитика для бизнес-пользователей.|Apache Superset / Tableau / Power BI|BI — единый интерфейс для аналитиков. Потребляет данные из DWH (регламентированная отчётность) и Lakehouse (исследовательская аналитика).|Витрины, Дашборды, Метрики|SQL-запросы к DWH. Дашборды для аналитиков и руководства.|

5. #### Слой оркестрации и управления данными

|компонент|Назначение|Технология|Обоснование выбора|Принцип работы|
|:-:|:-:|:-:|:-:|-|
|Apache Airflow|Оркестрация batch-пайплайнов: запуск выгрузок из Core в Lakehouse, ELT из Lakehouse в DWH, обновление витрин.|Apache Airflow + Kubernetes|Airflow — стандарт де-факто для оркестрации DAG-пайплайнов. Обеспечивает мониторинг, повторные запуски при ошибках, управление зависимостями.|DAG: Core → Lakehouse (daily). DAG: Lakehouse → DWH (daily). DAG: DWH → BI (daily).|
|DataHub|Каталог данных, lineage, владельцы. Автоматически собирает метаданные из всех систем.|DataHub (LinkedIn) / Apache Atlas|DataHub решает проблему “что где лежит” и “откуда данные”. Lineage (от CDC до BI) критичен для аудита и доверия к данным. Без каталога — хаос в 50+ таблицах и 100+ топиках Kafka.|Metadata из: CRM, Core, Cards, Loans, DWH, Lakehouse, Kafka, MDM, ESB, Airflow, BI|
