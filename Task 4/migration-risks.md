### Таблица рисков миграции FinUnion + RetailBank



|Риск|Влияние|Вероятность|Митигация|
|:-:|:-:|:-:|:-:|
|Потеря данных при миграции — при batch-выгрузке из RB Core в FU Core произошёл сбой (обрыв сети, ошибка Spark, повреждение Parquet-файлов). Часть данных (транзакции, договоры) не загружена в целевое хранилище.|Критическое: расхождение балансов, неполная отчётность, штрафы ЦБ, судебные иски клиентов при неверных остатках.|Низкая (10%)|1. Exactly-once семантика Spark + Iceberg (commit/rollback). <br />2. Контрольные суммы до и после загрузки (количество записей, сумма остатков). <br />3. Retry-логика Airflow (3 попытки). <br />4. Параллельная работа систем (30 дней): сверка Fed DWH vs FU Core + RB Core. <br />5. Резервное копирование RB Core до отключения (30 дней retention).|
|Простой клиентских сервисов — при отключении RB Core и переключении на FU Core возникла ошибка маршрутизации в ESB/API Gateway. Клиенты не могут провести платёж или получить выписку.|Критическое: остановка обслуживания клиентов на 2-4 часа, репутационный ущерб, жалобы в ЦБ, финансовые потери (комиссии, проценты).|Средняя (30%)|1. Blue-green развёртывание: RB Core работает параллельно 30 дней. <br />2. Автоматический rollback при ошибке (переключение на RB Core за 5 минут). <br />3. Нагрузочное тестирование ESB/API Gateway (200% пиковой нагрузки). <br />4. Мониторинг (Prometheus + Grafana) с алертами при задержке > 1 сек. <br />5. Runbook для ручного переключения.|
|Несовместимость форматов данных — после маппинга справочников (типы счетов, статусы договоров, валюты) в Fed DWH остались расхождения. Форма ЦБ (Баланс) не сошлась: остатки FU Core и RB Core не совпадают на 0.5%.|Высокое: неверная отчётность, ручные сверки (10+ часов в неделю), недоверие к данным со стороны бизнеса, задержки в принятии решений.|Средняя (40%)|1. Маппинг справочников (3 месяца до загрузки) с утверждением бизнесом. <br />2. Автоматическая валидация: контрольная сумма после ETL (Fed DWH = FU Core + RB Core). <br />3. Параллельная работа (3 месяца): сверка Fed DWH и старых DWH. <br />4. Автоматическая остановка DAG при расхождении > 0.01%. <br />5. DataHub для отслеживания lineage и быстрого поиска ошибки.|
|Утечка персональных данных при миграции — данные клиентов (ФИО, паспорт, ИНН, телефон) передаются через Kafka (CDC) без шифрования или с нарушением RBAC. MDM хранит ПДн в открытом виде.|Критическое: штраф, уголовная ответственность, репутационный ущерб, отзыв лицензии ЦБ.|Низкая (15%)|1. Сквозное шифрование TLS 1.3 для всех каналов (Kafka, ESB, API Gateway). <br />2. Маскирование ПДн в логах (кроме аудита). <br />3. RBAC: доступ к MDM только для Data Office. <br />4. Аудит доступа к MDM (DataHub + SIEM). <br />5. Пентест перед запуском MDM. <br />6. DLP-система для контроля передачи данных.|
|Отказ Kafka при пиковой нагрузке — во время массовой миграции клиентов (5 млн записей) Kafka не выдержала пропускную способность. Часть событий потеряна (Duplication или OOM).|Высокое: потеря изменений клиентов (дубли, неполная золотая запись), расхождение MDM и CRM, неверная отчётность.|Средняя (25%)|1. Тестирование нагрузки (200% пиковой: 10 млн событий/час). <br />2. Партиционирование топиков (16 партиций). <br />3. Replication factor = 3 (отказоустойчивость). <br />4. Мониторинг lag (Grafana, алерт при lag > 5 минут). 5. Dead Letter Queue (DLQ) для необработанных сообщений.|
|Конфликт golden\_id при матчинге клиентов — MDM объединил разных клиентов (разные ИНН, но одинаковые ФИО и дата рождения) под одним golden\_id. Клиенты получили доступ к чужим счетам и картам.|Критическое: финансовые потери (доступ к чужим счетам), судебные иски, репутационный ущерб, штрафы ЦБ за нарушение банковской тайны.|Низкая (5%)|1. Правила матчинга: приоритет ИНН (100% совпадение) > паспорт (100% серия+номер) > ФИО+дата рождения (fuzzy). 2. Подтверждение спорных случаев: ручная верификация 10% выборки. <br />3. Аудит: логирование всех объединений (DataHub). <br />4. Возможность разъединения (rollback golden\_id) через MDM API.|
|Долгий перевыпуск карт RB Cards — физический перевыпуск 2 млн карт в FU Cards занимает 12+ месяцев. Клиенты не могут получить новую карту в отделении RB (отделения закрыты), а в FU — карта ещё не выпущена.|Среднее: снижение NPS, отток клиентов, потеря комиссионного дохода (1-2% от карточного портфеля).|Высокая (60%)|1. Перевыпуск по истечении срока (основной сценарий). 2. Принудительный перевыпуск только при обращении (утеря, блокировка). <br />3. Продление срока действия карт RB Cards на 6 месяцев (если возможно). <br />4. СМС-уведомления клиентам за 30 дней до истечения срока. <br />5. Ускоренный перевыпуск (FU Cards — 3 дня вместо 7).|
|Неготовность персонала к новой CRM — сотрудники контакт-центра и отделений не обучены работе с FU CRM. После отключения RB CRM — звонки не обрабатываются, заявки не создаются, время обслуживания выросло с 5 до 15 минут.|Высокое: снижение NPS (с 70 до 40), жалобы клиентов, недовольство руководства, срыв SLA контакт-центра.|Высокая (50%)|1. Обучение: за 2 месяца до переключения. <br />2. Super-users: 10% сотрудников проходят углублённое обучение (поддержка коллег). <br />3. Параллельная работа CRM (2 недели после переключения: RB CRM доступна для справок). <br />4. Тестовые сценарии (100 типов обращений). <br />5. Мониторинг AHT (Average Handle Time) после переключения.|
|Расхождение отчётности после отключения RB DWH — при формировании формы ЦБ за прошлый месяц данные из RB DWH не совпадают с Fed DWH (из-за ошибки маппинга или неполной загрузки). Отчётность сдана с ошибкой.|Высокое: штраф ЦБ, предписание, внеплановая проверка, репутационный ущерб.|Низкая (10%)|1. Параллельная работа DWH (3 месяца): Fed DWH + RB DWH. <br />2. Автоматическая сверка после каждого batch. <br />3. Контрольные суммы (количество записей, итоговые значения). <br />4. RB DWH отключается только после 3 успешных сдач отчётности из Fed DWH.|
|Перегрузка API Gateway при переключении — после отключения RB P2P все запросы клиентов и сотрудников пошли через API Gateway. Нагрузка выросла на 300% (с 10 тыс до 40 тыс запросов/сек). API Gateway не выдержал, часть запросов отклонена (503).|Среднее: недоступность сервисов (2-3 часа), жалобы клиентов, потеря операций.|Средняя (30%)|1. Нагрузочное тестирование (400% пиковой нагрузки). <br />2. Автомасштабирование (Kubernetes HPA: 3 → 10 подов). 3. Rate limiting (1000 запросов/сек на клиента). <br />4. Кэширование (Redis) для частых запросов (выписки, остатки). <br />5. Мониторинг (алерт при загрузке > 70%).|
