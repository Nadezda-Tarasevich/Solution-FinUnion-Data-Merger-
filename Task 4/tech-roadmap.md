### Технологическая дорожная карта FinUnion Group (12 месяцев)



###### Зона 1: Фундамент (0-3 месяца)


Цель: Быстро получить единую отчётность, запустить MDM и первые дашборды. Используются только знакомые технологии, чтобы минимизировать риски на раннем этапе.

|Компонент|Роль в целевой архитектуре|Почему попал в эту зону|
|:-:|:-:|:-:|
|PostgreSQL (Fed DWH + MDM)|Fed DWH для консолидации отчётности FU + RB. MDM для золотой записи клиентов.|PostgreSQL — знакомая технология для команды FinUnion. Не требует найма новых специалистов. За 3 месяца можно развернуть Fed DWH, загрузить данные из FU DWH и RB DWH, настроить MDM и выполнить первичную дедубликацию клиентов. Это «быстрая победа», которая демонстрирует ценность проекта бизнесу (единая отчётность за 3 месяца). На поздних этапах Fed DWH будет заменён на ClickHouse, но PostgreSQL останется для MDM.|
|Apache Airflow|Оркестрация всех batch-пайплайнов: выгрузка из FU DWH и RB DWH, загрузка в Fed DWH, ELT в ClickHouse, обновление витрин.|Airflow — стандарт де-факто для оркестрации DAG-пайплайнов. Без оркестрации ETL-процессы будут ручными и ненадёжными. Airflow выбирается на 1-м месяце, потому что будет использоваться на всех последующих этапах (ClickHouse, Spark, Iceberg). Инвестиция в будущее.|
|PostgreSQL FDW (Foreign Data Wrapper)|Федеративные запросы к FU DWH и RB DWH как к локальным таблицам.|FDW — самый простой способ собрать Fed DWH без сложного ETL. Не нужен Spark, не нужна Kafka. На 3 месяцах это оправдано скоростью внедрения. На этапе 3 FDW будет заменён на Spark + Iceberg.|
|Python + SQL (ETL-скрипты)|Трансформация данных при загрузке в Fed DWH: маппинг справочников, дедубликация клиентов, валидация.|Команда FinUnion знает Python и SQL. Писать ETL на Python быстрее, чем внедрять новый инструмент. На этапе 3 Python-скрипты будут заменены на Spark (для обработки 15 млрд строк).|
|Apache Superset (BI)|Дашборды для аналитиков: единая отчётность по клиентам, счетам, продуктам.|Open-source BI-инструмент, который подключается к PostgreSQL. Не требует лицензий. На 3 месяцах нужно быстро показать бизнесу единые дашборды — Superset справляется с этой задачей. Останется и на поздних этапах (подключается к ClickHouse).|



###### Зона 2: Интеграция (3-6 месяцев)



Цель: Построить событийно-ориентированную архитектуру, настроить CDC, API Gateway и ESB для миграции данных между RB и FU.

|Компонент|Роль в целевой архитектуре|Почему попал в эту зону|
|:-:|:-:|:-:|
| Kong/API Gateway|Единая точка входа для всех внешних запросов (клиенты, сотрудники, партнёры). Маршрутизация в CRM, Core, Cards.|API Gateway выбирается на 3-6 месяц, потому что к этому моменту начинается миграция клиентов, и нужно маршрутизировать запросы между старой (RB) и новой (FU) системами. Без API Gateway каждая система имеет свой API, что усложняет интеграцию. Kong — open-source, легко масштабируется.|
|Apache Kafka|Центральная событийная шина для всех потоков данных. Используется для CDC, событий, интеграции с MDM и аналитическим слоем.|Kafka выбирается на 3-6 месяц, потому что к этому моменту уже есть MDM (золотая запись клиента) и нужно синхронизировать данные между системами в реальном времени. Kafka — сложная технология, требующая отдельной команды, поэтому её внедрение откладывается на 3 месяц (после стабилизации фундамента).|
|Debezium (CDC)|Захват изменений данных из операционных БД (PostgreSQL) в реальном времени. Пишет изменения в Kafka.|Debezium — стандартный инструмент для CDC. Тесно связан с Kafka. Без CDC невозможно захватывать изменения в MDM и Fed DWH в реальном времени. Выбирается на 3-6 месяц вместе с Kafka.|
|Apache Camel / ESB|Внутренняя шина для синхронного обмена между операционными системами (CRM, Core, Cards, Loans). Маршрутизация, трансформация, retry.|ESB выбирается на 3-6 месяц, потому что к этому моменту начинается миграция потоков данных. Без ESB системы общаются напрямую (point-to-point), что уже является проблемой в As-Is. ESB централизует маршруты и обеспечивает слабую связанность.|



###### Зона 3: Аналитика (6-9 месяцев)



Цель: Масштабировать аналитическую платформу для обработки больших данных (15 млрд транзакций, 3.7 ТБ исторических данных).

|Компонент|Роль в целевой архитектуре|Почему попал в эту зону|
|:-:|:-:|:-:|
|ClickHouse|DWH для регламентированной отчётности (формы ЦБ, МСФО, управленческая отчётность). Заменяет PostgreSQL Fed DWH.|ClickHouse выбирается на 6-9 месяц, потому что к этому моменту объём данных в Fed DWH превышает 10 ТБ (после миграции исторических транзакций RB). ClickHouse в 10-100 раз быстрее PostgreSQL на агрегациях. Обеспечивает выполнение форм ЦБ за < 1 часа (ранее — 2-3 дня).|
|Apache Spark|Распределённая обработка данных для ELT из Data Lakehouse в DWH. Агрегация 15 млрд транзакций, построение витрин.|Spark выбирается на 6-9 месяц, потому что к этому моменту исторические данные (FU + RB) загружены в Data Lakehouse, и требуется распределённая обработка. Spark заменяет Python-скрипты, которые не справляются с объёмом 15 млрд строк.|
|Apache Iceberg|Формат таблиц для Data Lakehouse с ACID, schema evolution, time travel. Хранение исторических транзакций и событий из Kafka.|Iceberg выбирается на 6-9 месяц, потому что к этому моменту в Lakehouse накоплено достаточно данных (3.7 ТБ), и требуется ACID для ELT-процессов. Iceberg — open-source, стандарт для Data Lakehouse.|
|S3 / MinIO (объектное хранилище)|Хранение данных Data Lakehouse (Parquet, Iceberg) и архива (S3 Glacier).|S3 выбирается на 6-9 месяц, потому что к этому моменту объём данных превышает ёмкость локальных дисков PostgreSQL (3.7 ТБ). S3 обеспечивает дешёвое хранение (\~$5/TB/мес) и горизонтальное масштабирование.|



###### Зона 4: Управление (9-12 месяцев)


Цель: Обеспечить прозрачность, качество и управляемость данных во всей архитектуре.

|Компонент|Роль в целевой архитектуре|Почему попал в эту зону|
|:-:|:-:|:-:|
|DataHub|Каталог данных с автоматическим сбором lineage. Фиксирует схемы, владельцев, происхождение данных от CDC до BI.|DataHub выбирается на 9-12 месяц, потому что к этому моменту все системы (ClickHouse, Iceberg, Kafka, Airflow) уже запущены, и нужно фиксировать их метаданные. Без DataHub через 12 месяцев в 50+ таблицах и 100+ топиках Kafka будет хаос. DataHub — заключительный элемент, который делает архитектуру управляемой.|
|Prometheus + Grafana (мониторинг)|Мониторинг всех компонентов: Kafka lag, ClickHouse latency, Airflow DAG status, загрузка CPU, сеть.|Мониторинг выбирается на 9-12 месяц, потому что к этому моменту количество компонентов становится критическим (10+ сервисов), и без мониторинга невозможно гарантировать SLA. Prometheus + Grafana — стандартный стек для мониторинга.|
